# Date Nite

A static site (`index.html`, `venues.json`) mapping restaurants with an estimated "date night" cost. Venues are added by GitHub Actions workflows that read each restaurant's menu and save five prices per venue. This file is mainly for improving that menu importer.

## The menu importer

- `add_venue_from_issue.py` is the importer. It tries sources in order and falls back down the list: pasted menu text, the restaurant's own site (plain request, then a headless Playwright browser), linked PDF/image menus, Gemini reading the site, the Menu tab of the venue's Google Maps listing (`pricing_from_google_maps_menu`, a headless browser; off unless `MAPS_MENU=1`, because Google serves a signed-out browser a limited listing with no Menu tab, logged as `maps_menu: limited_view`; test it on a runner with the `Maps Menu Probe` workflow, `maps_menu_probe.py`, which needs no keys), then Claude web search (`claude_search_pricing`), after which the venue's Yelp menu page is tried when the search found its Yelp listing (`pricing_from_yelp_menu`). There is no Gemini web search in the importer: it was removed on Nov 26 (see below). A venue Claude's search finds no sourced prices for gets no prices (the grid and city imports skip it; the Add Venue form asks for the menu). Gemini prompts live in `PDF_PROMPT`, `SCOPE_RULES` and `SEARCH_PRICING_PROMPT` near the top.
- Chains: `add_city.eligible()` (used by the grid and city searches) refuses fast-food chains (`BLOCKED_CHAINS`) and the sit-down and fast-casual chains listed in `excluded-chains.json` (matched by `chains.py` on the start of the name, so "Chili's Grill & Bar" and "Home Run Inn Pizza - Bolingbrook, IL" both match; an entry starting with `=` must match the whole name, as `=CAVA` does, so a local "Cava Tapas Bar" still qualifies). Shake Shack and Velvet Taco are in that list too (added Nov 26 at the owner's request, reversing the old rule that allowed higher-end fast casual); Taco Pros and Velvet Taco are also in `excluded-venues.json`. Edit the file to add or drop a chain. The Add Venue form is not checked, because a person chose that venue.
- Fallback diagnostics: `response_shape` and `grounding_summary` (used by the probes) describe what a Gemini response held, and a `claude_fetch failed` with no url carries the tool input Claude sent. `Gemini Probe` (`gemini-probe.yml`, `gemini_probe.py`, needs the Gemini key, a few cents) runs the importer's search prompt for one venue with five settings (default, thinking LOW, MINIMAL, budget 0, no temperature) and prints whether grounding came back and what each cost. Its `probe` input also offers `search-and-thinking` (`gemini_probe2.py`, capped at $0.40, `part` input: `thinking` is five cheap extraction calls on a made-up menu with known answers to see whether a lower thinking level changes what is read; `search` is grounded searches, which Google bills per query and the model chooses how many, so one call can run 8 and cost about $0.28).
- Gemini web search (removed Nov 26): the Nov 25 probes showed the model does search with the importer's JSON-only prompt, but the searches are invisible without `tool_config include_server_side_tool_invocations` (`gemini_usage.search_queries_in` counts them from the `GOOGLE_SEARCH` tool calls, and the usage log and budget gate now price them). On the first scheduled grid run the search ran 16 queries for each of two venues, an estimated $0.56 each (the $0.035 per query rate is unverified), and gave one set of untraceable estimates and one empty answer, so the importer's Gemini search step was removed and Claude's search (about $0.13 a venue on Nov 25) runs instead. `SEARCH_PRICING_PROMPT` is still Claude's prompt. The weekly refresh (`batch_update_venues.py`) and `update_venues.py` still have their own Gemini searches; check the cost before turning the refresh back on.
- Thinking: the calls that read prices from menu text or a PDF/image menu use `extraction_config()` (Gemini thinking level LOW; set `GEMINI_EXTRACTION_THINKING` to MINIMAL, MEDIUM or HIGH, or to `default` to restore the model's own thinking). The Nov 26 probe read a made-up menu identically at LOW, MINIMAL, budget 0 and the default, while the default spent about 1,200 thinking tokens on a 204-token answer. The call that opens a site (`url_context`) keeps the default; the probe did not test it. Image and PDF reads were not in the probe, only text.
- Output per venue: `app`, `casualMain`, `premiumMain`, `drink`, `dessert` (medians of the category lists, with stand-in numbers when a category is empty), total = (app + casualMain + premiumMain + 2*drink + dessert) * 1.30, mapped to a tier color. Taco places count two casual mains.
- `clean_pricing` (which also drops appetizers that outprice the casual mains, `pricing_rules.apps_look_misfiled`), `price_count` (needs at least 6 price-like numbers), `price_sanity_warnings` and `pricing_rules.py` hold the cleaning and sanity rules. Change those rather than duplicating logic.
- Workflows that run the importer: `add-venue.yml`, `add-city.yml`, `search-cells.yml`, `add-menu.yml` (someone replies to a `needs-menu` or `double-check` issue with pasted menu text), or with only `key: price` lines to override some prices; `price_overrides_from_reply` is strict, so one non-matching line makes the reply menu text). Each ends with `python menu_log.py publish`.
- Dependencies: `requirements.txt` (google-genai, playwright, anthropic). Keys (Gemini, Anthropic) exist only in Actions secrets, so full end-to-end runs are not possible in a local or cloud session. Test pieces in isolation.

## Spend tracking and the budget gate

- `gemini_usage.py` logs every Gemini call (tokens, grounding queries) through the importer's client and publishes it to `usage.jsonl` on the `gemini-usage` branch; each workflow that holds the Gemini key ends with `python gemini_usage.py publish`. `RUN_BUDGET_USD` makes a run stop calling Gemini once its estimated spend passes that figure (logged as `gemini run_budget_reached`).
- `budget.py` prices the week (Gemini log plus the `search_claude` steps in the menu log) against the repository variable `WEEKLY_BUDGET_USD`, paces it over the days left in the Pacific Monday-Sunday week, and `python budget.py gate` prints `proceed`, `run_budget_usd`, `allowed_venues` and `max_cells` for a scheduled workflow. Dollar rates are in `budget.RATES` (override with `BUDGET_RATES_JSON`). The `AI Budget` workflow prints the report. Places requests keep their own daily limit in `places_usage.py`. A venue is priced at the larger of the measured average and `PER_VENUE_USD_DEFAULT` until five venues have been imported since Gemini logging began.
- `daily-search.yml` (`Daily Grid Search`, cron 10:41 UTC, also manual with a `dry_run` option) waits for earlier importer runs, runs the gate, lets `pick_cells.py` choose the cells (unsearched, not water, not full, not in an open cell pull request, ranked by venues in the cell and its neighbours), opens an issue for the pull request to close (`venue_review.py` finds `venue-review/cells-<issue>.json` by that number), runs `add_cell.py` with `RUN_BUDGET_USD`, and opens the usual Search Grid Cells pull request with Approve / Deny boxes. After `add_cell.py`, `triage.py decide` sets Approve / Deny / Hold per venue, and the repository variable `AUTO_TRIAGE` picks what happens: `off` (pull request as before, boxes empty), `suggest` (the default: the pull request's boxes are ticked and a table gives each reason, a person still merges) or `apply` (the run folds approved venues into `main` itself with `triage.py apply` plus `venue_review.write_pending` / `fold_pending_venues`, adds denied ones to `excluded-venues.json`, opens `venue-review` issues for held ones, and posts the table with undo steps on the run's issue; a push or merge made with the workflow token starts no other workflow, which is why it does not open and merge a pull request). Approve needs a clean `menu_read` from the restaurant's own site, link or PDF, no flags, a town and state, and no similar nearby venue; Deny is only the same website within 150 m of a venue on the map; everything else is held (rules and `AUTO_APPROVE_MAX` in the `triage.py` docstring). It does nothing when the gate says stop, when `MAX_OPEN_CELL_PRS` (variable, default 3) cell pull requests are open, or when no cells are left. `add_city.py` runs the importer as a separate process per venue, so the run's spend is summed from the shared log file (`gemini_usage.run_cost`); once spent, pricing stops and a cell that was cut short is not marked searched.

## The failure log (start here when improving the importer)

- `menu_log.py` writes one JSON line per venue per importer run. Lines are appended to `menu-log.jsonl` on the `menu-log` branch, which is kept off `main` so logging never triggers a site rebuild. The record format and the list of step/result words are in the module docstring. Read it before analyzing.
- Read it back:

```bash
git fetch origin menu-log
python menu_log.py report --recent 20    # outcomes, failure reasons, problem sites, venues with no real menu
python menu_log.py export > /tmp/menu-log.jsonl   # raw records for deeper analysis
```

- Key signals: `outcome` (`menu_read`, `menu_read_partial`, `web_search_only`, `none`, `reply_unreadable`, `incomplete`), `steps` (every attempt with `step`, `result`, `host`, `platform`), and `reply: true`, meaning a person pasted the menu, which is ground truth the importer missed.
- The log stores counts and prices, not menu text or page HTML. If a failure cannot be diagnosed from the log alone, ask for the venue's menu URL or pasted text rather than guessing.
- The `Menu Import Log` workflow (`menu-log.yml`) prints the same report from the Actions tab.
- When the importer learns a new way to fail, add a new result word in `add_venue_from_issue.py` via `menu_log.step(...)` and list it in the `menu_log.py` docstring. Logging must never raise or block a venue from being added.

## How to work on importer improvements

1. Run the report, pick the most common failure reason or problem platform, and look at the specific records behind it.
2. Reproduce with the smallest piece you can run without keys (for example `fetch_url`, `html_to_text`, `menu_page_candidates`, `price_count`, `clean_pricing`), or with `menu_prices.py`.
3. `/menu-prices` (`.claude/commands/menu-prices.md`, backed by `menu_prices.py`) turns an uploaded menu into the five prices using the importer's own functions. Use it to check what a corrected extraction should produce.
4. Keep changes narrow and name the failure reason being fixed. Say plainly what could not be tested without API keys.
5. Do not edit `venues.json` directly for importer work unless asked. It is changed by workflows and stamped with version commits.

## Repo notes

- `main` auto-deploys the site (CNAME, GitHub Pages) and `stamp-version.yml` adds "Stamp version N" commits. Do not hand-edit those stamps.
- Other data branches exist, such as `places-usage` (same pattern as `menu-log`).
- `dashboard_stats.py` (workflow `dashboard-stats.yml`, nightly) computes the numbers for the private dashboard page and saves them as `dashboard-stats.json` on the `dashboard-data` branch (one commit, replaced each run). Read it with `git fetch origin dashboard-data && git show origin/dashboard-data:dashboard-stats.json`. It reuses `menu_log.py`, `places_usage.py` and `grid_cells.py`, so change rules there, not in the stats script. Stale venues are those whose price or `lastUpdated` last changed over 30 days ago (`PRICE_FIELDS`).
- The weekly price refresh (`refresh-venues.yml`, `batch_update_venues.py`) is SUSPENDED (its cron schedule is commented out; manual runs still work) while Gemini spend is investigated after the cap was reached on Nov 15. When on, it re-prices the 40 least recently updated venues with a Gemini web search, using each venue's own town. It stamps `priceSource: "search"` on what it writes. It skips venues whose prices were read from the restaurant's own menu or changed by hand (`protection_reason`: `priceSource` of `hand` or `menu` set by Edit Venue, otherwise the `menu-log` record compared with the saved prices). Skipped venues never get a new `lastUpdated` from the refresh. They still get the closure check: each run also closure-checks the `CLOSURE_LIMIT` (default 20) protected venues with the oldest `closureCheckedAt` (never-checked first). Every closure check stamps `closureCheckedAt`, except one whose answer could not be read. The protection rule (`log_index`, `protection_reason`) lives in `menu_log.py` so the refresh and `dashboard_stats.py` use the same one; the dashboard lists protected venues that are going stale apart from the rest, since only a re-read menu refreshes them. With no `TARGET_VENUE` it stops if the `menu-log` branch cannot be read. A `TARGET_VENUE` run refreshes that venue regardless.
- `maps-menu-bookmarklet.html` (install page, served by the site) and `maps-menu-bookmarklet.js` (its source) are one browser bookmark that sends a menu to the importer from the user's own browser. On a Google Maps listing (signed in) it reads the Menu tab and opens the `add-venue-from-link.yml` form (`maps_link`, `menu_text`). On any other page (`anySite`: the restaurant's own website, Uber Eats, Postmates, other ordering sites) it reads dishes and prices from schema.org data or the page as drawn, shows a panel of sections to tick, and opens `edit-venue.yml` (`venue_name`, `town`, `state`, `menu_text`) or, for a new venue, `add-venue.yml` (`venue_name`, `address`, `website`, `menu_text`). A third choice, for a venue held in Venue Review, copies the menu to the clipboard and opens a search for that venue's open `venue-review` issue, where it is pasted as a comment (`venue-review-menu.yml`). Ticked sections can be kept in the site's `localStorage` (`datenite-basket`) across pages of one site. It depends on those forms' field ids. It cannot read PDFs, images or framed menus. The source is fetched when the bookmark is dragged, so a change to the `.js` reaches a user only when they install it again.
- Venue add/remove/audit scripts (`add_venue_from_issue.py`, `remove_venue_from_issue.py`, `audit_venues.py`, `batch_update_venues.py`, `fold_pending_venues.py`) are driven by issues.
- Editing a venue already on the map: the "Edit a Venue" issue form (`edit-venue.yml` workflow, `edit_venue_from_issue.py`). Name, town and state are required. `venue_match.py` finds the venue generously (case, punctuation, filler words, typos, town name in the venue name) and refuses an ambiguous name instead of guessing. Pasted menu text (read with the importer's `pricing_from_menu_text`) and `key: price` overrides replace saved prices; blanks keep saved values. It never searches the web, never adds `needs-menu` or `double-check` labels, and always closes the issue. `venue_match.py` is standard-library only, so it can be tested locally without keys. `grid/`, `grid_cells.py`, `add_cell.py`, `split_cells.py` manage the Places search grid. Search Grid Cells and Split Grid Cells pull requests all edit `grid/grid.json`, so they conflict with each other. `.github/scripts/merge-main-into-branch.sh` (uses `merge_grid.py`) brings a branch up to date with `main`, resolving a `grid.json`-only conflict. `search-cells.yml` and `split-cells.yml` run it just before opening their pull request, because a run can last many minutes and its `main` goes stale; `refresh-cell-prs.yml` runs it on every open cell branch whenever `main`'s `grid/grid.json` changes. A pull request opened with the workflow token does not trigger workflows, so the refresh cannot cover a branch that was already stale when it opened.
